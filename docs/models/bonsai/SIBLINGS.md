# Bonsai-8B (2-bit) — Sibling-Backend Champions (Phase A)

> Companion: `rMLX.md` — rMLX full matrix + standing-vs-champion (**complete**).
> This file covers sibling backends only.
> Mirrors [`../gemma4/SIBLINGS.md`](../gemma4/SIBLINGS.md) in protocol and shape.

**Model:** `prism-ml__Ternary-Bonsai-8B-mlx-2bit` —
`Qwen3ForCausalLM`, dense ~8B, **2-bit affine** weights (group 128), full
attention (`sliding_window: null`), **YARN rope ×4** (native 16384 → 65536).
Single snapshot (not a multi-model family), so there is one decode table.
**Stage 1 (Phase A) collected:** 2026-06-23
**Machine:** Apple M5 Max, 128 GB unified memory, macOS 26.5.1 (Darwin 25.5.0)
**Protocol:** batch=1 single-stream; temp=0 (greedy); `max_tokens=256`;
n=5 requested per cell (1 warmup `r0` discarded → **n=4 measured**) at
4k/8k/16k/32k; **n=2 requested → n=1 measured** at 64k. Decode-TPS medians from
the measured runs; 95% CI via bootstrap (2000 samples, seed 20260623) where n≥2.
Tables generated by `Cross-Backend-Bench/scripts/agg_bonsai_siblings.py` from
`metrics/runs/*.jsonl` — not hand-typed.

## 0. TL;DR

- **mlx-lm (no KV quant) is the Bonsai decode champion at every size ≥ 8k.** At
  4k it ties mlx-lm-turboquant within noise; from 8k up it pulls clear.
- **mlx-lm-turboquant's KV 8,4 (fake-asym) *loses* on Bonsai** — the opposite of
  the Qwen3.6 result. Bonsai's 2-bit weights make the weight stream tiny, so
  there is little bandwidth headroom for KV quant to recover, while the
  fake-asym dequant adds per-step compute. tq trails mlx-lm by 2–11 % at every
  size ≥ 8k and its **prefill is also slower** (74 s vs 61 s at 64k).
- **oMLX trails the mlx-lm tier at every size and collapses at 64k.** Even for an
  8B model it forces a paged KV cache: decode falls to **4.0 TPS at 64k** (RSS
  climbs 3.3 → 16.8 GB — I/O-bound, not compute) and its prefill is a
  prefix-cache artifact (r0 TTFT ~30–140 ms, "142k–668k tok/s"). Not
  championable at long context.
- **There is no 128k cell** — `max_position_embeddings = 65536`, so 64k is the
  ceiling. Unlike the Gemma4 e2b/e4b 128k problem, the standard
  `prompts/longctx_64k.json` **fits**: it is ~63.3k tokens under the Bonsai
  tokenizer (the Qwen3.6 tokenizer counts it as ~65.5k), leaving ~2k headroom
  after the chat template + 256 generated tokens. No custom fixture needed.
- **Coherence holds to 64k.** Every backend, every benched size, produced
  on-task output under YARN ×4 — no degeneration at 4× the native 16384 context.
- **ollama, paroquant, mlx-vlm** are skipped — see §4.

## 1. Snapshot in Scope

`ls $RMLX_O_MODELS_ROOT | grep -i bonsai` enumerates one snapshot. All three
benched siblings load the **same 2-bit affine weights** → directly
weight-comparable; `mlx-lm-turboquant` additionally quantizes KV to 8,4.

| Snapshot (basename) | Weight quant | Arch / size | Role | Disk | Max ctx |
|---|---|---|---|---|---|
| `prism-ml__Ternary-Bonsai-8B-mlx-2bit` | affine g128 b2 (ternary) | `Qwen3ForCausalLM` dense, ~8B | **bench target** (rMLX test-target family) | 2.2 GB | 65536 |

Architecture facts (from `config.json`, drive the bench design):

| Fact | Value | Consequence |
|---|---|---|
| `num_hidden_layers` | 36 | — |
| heads (attn / kv) | 32 / 8 (GQA) | KV is 8 heads × 128 dim |
| `sliding_window` | `null` (full attention) | resident KV grows linearly with context — no SWA bound |
| `max_position_embeddings` | **65536** | **ctx ceiling 64k — no 128k cell** |
| `rope_scaling` | YARN, factor 4.0, native 16384 | 64k = 4× native; coherence past 32k previously untested (now verified, §5) |
| weight quant | 2-bit affine, group 128 | tiny weight stream → decode is **not** weight-bandwidth bound the way the larger mxfp8 models are |

Stock mlx-lm loads Qwen3 cleanly — it does **not** hit the Gemma4 KV-shared
`sanitize()` bug — so the plain-mlx-lm reference here is **stock** mlx-lm, not
the turboquant-fork plain build the Gemma4 e2b/e4b rows had to use.

## 2. Sibling Champion Table (decode TPS, weight-comparable 2-bit tier)

Decode TPS = median of measured runs at steady-state (tokens 2…end), temp=0,
`max_tokens=256`. **All three benched siblings carry affine g128 b2 weights** →
directly weight-comparable. `mlx-lm-tq` additionally quantizes KV to 8,4
("fake-asym" per the fork — not the true K8/V4 codec rMLX implements). Champion
per row in **bold**. `oMLX` decode shown but see §3 caveats.

### 2a. Decode TPS

| Prompt | mlx-lm (no KV) | mlx-lm-tq (KV 8,4) | oMLX (no KV) | Champion |
|---|---|---|---|---|
| 4k | 109.8 [109.0–110.6] | **111.5 [99.0–112.5]** | 99.6 [99.4–100.9] | **mlx-lm ≈ tq** ¹ |
| 8k | **94.5 [79.1–95.7]** ² | 92.7 [92.2–92.8] | 75.7 [65.2–81.6] | **mlx-lm** |
| 16k | **73.2 [63.8–73.8]** ² | 64.9 [57.6–68.5] | 59.0 [51.4–66.0] | **mlx-lm** |
| 32k | **48.6 [45.0–49.4]** | 44.3 [34.2–45.6] | 38.5 [5.4–45.3] ³ | **mlx-lm** |
| 64k⁴ | **28.5** | 25.1 | 4.0 (paged) | **mlx-lm** |

¹ 4k is a statistical tie: tq's nominal median (111.5) is ~1.5 % above mlx-lm
(109.8) but its CI lower bound (99.0) is dragged by one warm-up-contaminated
measured run; mlx-lm's CI is tight ([109.0–110.6]). tq is *not* ahead from 8k up.

² Wide CI lower bound is a warm-up artifact — the first *measured* run (`r1`) at
8k (79.1) and 16k (63.8) is still partially cold; runs `r2`–`r4` are stable
(~95 / ~73.7). The median is robust; the CI lower bound is contaminated.

³ oMLX 32k CI [5.4–45.3]: `r1` is a 5.4 TPS cold/paging outlier (first
full-context allocation). Median (~38.5) reflects the warm runs.

⁴ **64k: n=1 measured** (single run after the discarded warm-up) — point
estimate, no CI. Prefill-dominated and expensive; decode is stable across the
short-ctx n=4 runs, so the 64k point estimate is a trustworthy trend anchor, not
a CI-bounded comparison.

### 2b. Prefill (cold, mlx-lm tier)

Cold first-request TTFT (`r0`, true uncached prefill). **oMLX prefill is
excluded** — its auto-prefix-cache returns r0 TTFT ~30–140 ms regardless of
context (cache hit, not prefill; "142k–668k tok/s" is the cache-hit rate). The
turboquant fork's quantized-KV path makes prefill **slower**, not faster, so
both are shown.

| Backend | 4k | 8k | 16k | 32k | 64k |
|---|---|---|---|---|---|
| mlx-lm (no KV) | 1.6 s / 2.5k t·s | 1.7 s / 4.9k | 4.2 s / 3.9k | 18.1 s / 1.8k | **60.7 s / 1.1k** |
| mlx-lm-tq (KV 8,4) | 1.3 s / 3.1k | 3.3 s / 2.5k | 9.7 s / 1.7k | 25.8 s / 1.3k | 74.2 s / 0.9k |

The **64k cold prefill is heavy** — 60.7 s TTFT at 64k (~1.1k tok/s) for mlx-lm,
74.2 s for tq. This is the headline prefill cost for the long-context Bonsai
cell, independent of decode. (Token-throughput here uses the fixture's
qwen3.6-tokenizer count; see §5 for the Bonsai-tokenizer actuals.)

## 3. Decode-efficiency analysis

**1. KV quant is a *net loss* on Bonsai decode.** On the Gemma4 mxfp8 models KV
8,4 was within ±2–4 % of plain mlx-lm (decode weight-bandwidth-bound, quant buys
nothing). On Bonsai it is worse: tq trails mlx-lm by 2 % (8k) → 11 % (16k) →
9 % (32k) → 12 % (64k). The reason is the 2-bit weights — the weight stream is
so small (2.2 GB) that decode is **not** dominated by weight bandwidth, and
Bonsai uses **full attention** (no SWA), so KV is the growing cost. But the
turboquant fork's fake-asym 8,4 path adds a per-step dequant that MLX does not
make cheaper than the bf16-KV flash path at these sizes, so the quant adds
compute without recovering enough bandwidth to pay for it. KV quant only helps
when the bandwidth saved exceeds the dequant cost; on Bonsai it does not, at any
benched context.

**2. tq prefill is slower than plain mlx-lm.** Quantizing KV during prefill costs
extra work on every chunk: 25.8 s vs 18.1 s at 32k, 74.2 s vs 60.7 s at 64k.
Combined with (1), the turboquant fork is strictly behind plain mlx-lm on Bonsai
for both phases — there is no cell where its KV 8,4 wins outside 4k noise.

**3. oMLX — two distortions, both make it non-championable at long context.**
   - *Decode trails the mlx-lm tier* by 9–20 % at 4k–16k even on warm runs.
   - *At 32k/64k it forces a paged KV cache.* RSS climbs 3.3 GB (4k) → 5.2 (16k)
     → 10.3 (32k) → 16.8 GB (64k), and decode collapses to **4.0 TPS at 64k** — pure
     paging I/O, not compute. The 32k `r1` (5.4 TPS) is the first cold paged
     allocation. These cells measure oMLX's tiering policy, not Bonsai's decode
     speed; **excluded from champion designation.**
   - *Prefill* is auto-prefix-cached: r0 TTFT ~30–140 ms at every context →
     prefill TPS is a cache-hit artifact ("668k tok/s" at 64k), not real
     prefill. Excluded from §2b.

**4. ollama has no Bonsai build.** Bonsai is an MLX-specific 2-bit *ternary*
quantization; ollama ships GGUF only, and there is no Bonsai/ternary MLX tag.
The comparison does not even arise (the historical CBB Bonsai rows have no ollama
column either).

## 4. Skips — non-benched backends / cells

| Backend / cell | Reason |
|---|---|
| **ollama** | No Bonsai (ternary 2-bit) MLX tag; ollama is GGUF, weight-format-incompatible with the affine-2bit safetensors. |
| **paroquant** / **isoquant** / **rotorquant** | Different weight schemes (rotation quant), non-weight-comparable to affine 2-bit; no live OpenAI-compatible CBB endpoint for Bonsai. Same pre-classified skips as the Gemma4 / Qwen3.6 campaigns. |
| **mlx-vlm** | Bonsai is a text-only model; mlx-vlm is a VLM reference. No applicable text-decode path. |
| **mistral.rs / llama.cpp / dynamo / 1bit-eval-scratch / experiments-kv-cache-compression / *-turboquant kernel variants** | No CBB runner and/or no OpenAI-compatible serving path and/or GGUF-only. Building runners is out of scope for a data-collection run. |
| **128k cell** | `max_position_embeddings = 65536` → 64k is the hard ceiling. No 128k fixture is run. |
| **rMLX (all cells)** | Phase A is siblings only; the rMLX full KV-quant matrix lives in `rMLX.md`. |

**Note on the 64k fixture (not a skip — a correction).** The standard
`prompts/longctx_64k.json` was flagged as a possible overflow risk because the
Qwen3.6 tokenizer counts it at ~65.5k tokens (> 65536 after template + gen). The
**Bonsai tokenizer counts the same text at ~63.3k** (chat-templated: 63,272
tokens), so with 256 generated tokens it lands at ~63.5k — ~2k under the ceiling.
The standard fixture is therefore used directly; the "64k" cell is a genuine
top-context measurement comparable to the other docs.

## 5. Notes

### Machine and environment
- **Chip:** Apple M5 Max, 128 GB unified memory
- **OS:** macOS 26.5.1 (Darwin 25.5.0)
- **Date:** 2026-06-23
- **Single-MLX discipline:** every backend switch preflighted
  (`scripts/_kill_mlx.sh`; rMLX claim released). One MLX process at a time.
- **No `purge` between cells** — macOS buffer cache may hold recently-read
  safetensors pages. Decode (steady-state) is insensitive; prefill r0 is cold
  per fresh server start.

### Coherence gate
Every benched cell passed temp=0 greedy coherence (real on-task text, no
repetition loop, non-empty, TPS>0) at 4k **and 64k**. Bonsai is a thinking model
(the chat template injects an empty `<think></think>` block); the strict
`task_pass_at_1` exact-3-line grader reports `False` on every run, but the output
is coherent and on-task — that is grader-format strictness, not degeneration.

| Backend | size | output sample | Verdict |
|---|---|---|---|
| mlx-lm | 4k | `llama.cpp: Contains detailed documentation and API changes, ` | PASS |
| mlx-lm | 64k | `llama.cpp: Contains detailed sections on installation, model` | PASS |
| mlx-lm-tq | 64k | `llama.cpp: Contains detailed sections on installation, model` | PASS |
| oMLX | 64k | `llama.cpp: Contains detailed sections on installation, model` | PASS |

**Coherence at 64k is the notable result** — Bonsai stays on-task at 4× its
native 16384 context (YARN ×4), extending the previously-recorded NIAH-32k PASS
to 64k on this summarization task.

### Tokenizer / fixture caveat
Prompt sizes are labeled by the **qwen3.6-tokenizer** fixture targets
(4096 / 8192 / 16381 / 32764 / 65528 tokens) for cross-doc comparability. The
**Bonsai tokenizer** packs the same text into fewer tokens — measured content
counts ≈ 3.7k / 7.7k / 15.6k / 31.5k / 63.3k. The prefill tok/s in §2b uses the
recorded (qwen3.6) count, so it is a slight over-estimate (~3 %) of the true
Bonsai prompt-token rate.

### Caveats carried into the rMLX matrix / synthesis
- 64k is **n=1 measured** — bump to n≥2 if a close call decides a champion.
- oMLX 32k/64k rows are **paging-policy artifacts**, not compute — do not crown
  or compare them.
- The **mlx-lm decode champion** (~110 / 94 / 73 / 49 / 28 TPS at 4k / 8k / 16k /
  32k / 64k) is the number rMLX is measured against. The rMLX matrix (`rMLX.md`)
  beats it at every context — `none` decode **133 / 115 / 90 / 61 / 36 TPS
  (+21…+27 %)**.
